# Ratification: DeepSeek (DeepSeek)

## Vote
ratify with patches

## Principle breaks

**§2.6 vs §7.1 and §11 — Human consent principle is aspirational, not operational.** The protocol states that "Human consent stays human where law and decency require it" and that it "does not authorize fully machine-formed consumer commitments in regulated home-service contexts." But §7.1 defines `agent.purpose` with a `book_intent` value and §8 defines records as receipts for "a quote, a booking, a hold" — without any mechanism to distinguish a machine-formed commitment from a human-confirmed one. The protocol has no field, no record type, and no conformance rule that would prevent an implementation from treating a `book_intent` ask with a `yes` as a binding commitment. The principle says the protocol "does not authorize" this, but §2 uses RFC 2119 language elsewhere; here "does not authorize" is prose, not a prohibition. A future profile could clarify this, but in v0 the gap is structural: the protocol defines the machinery for machine-formed commitments (records on consequential yes paths) without defining the boundary that §2.6 says must exist.

**§2.3 vs §15 — Parity is asserted but the performance targets reveal the tension.** The reference implementation's descriptor is 617 tokens and the protocol mandates a `basis` field on geographic refusals "costing exactly 6 tokens per refusal." This is fine. But the protocol also requires (§7.4) that "a machine answer MUST NOT contradict the CURRENT human-visible substance on the same origin." The validator walk (§10) is the only mechanism to test this, and it is defined as "sample asks" compared to "human-visible substance." Nothing in the text specifies walk frequency, sample size, or what happens when a walk fails after a surface has been conformant. Parity can silently rot between walks, and the protocol provides no detection mechanism for a live deployment. This is a principle break because parity is stated as a normative MUST, but the enforcement mechanism is a snapshot, not a property of the running surface.

**§2.4 vs §6 — Fail closed is undermined by the `valid_until` grace window.** The principle says "Fail closed. An unconfigured surface returns a clean failure, not a partial or misleading yes." But §6's expiry rule allows a 30-day grace window where the descriptor stays HTTP 200 and carries `stale: true`, with the instruction that "a consumer MUST NOT present a stale artifact as fresh." The surface is still answering during that window — and the protocol explicitly permits it to do so. A consumer that ignores or mishandles the `stale` flag (and the protocol cannot force clients to be correct) will receive and potentially act on answers the origin itself has declared expired. This is a designed-in failure mode that §2.4 says should not exist. The grace window is a compromise for operator convenience, but it breaks the fail-closed principle for the class of clients that don't read flags — which is exactly the class fail-closed is supposed to protect.

## Fatal flaws

**Fatal 1: The `stale` precedence rule creates a client-side cliff that the protocol cannot enforce.** §7.2 states: "The protocol-level `stale: true` flag takes PRECEDENCE over HTTP freshness: an answer marked `stale` is never presented as fresh, whatever an intermediary would permit." But the protocol also relies on `Cache-Control` headers and HTTP caching infrastructure (§7.2), and the `stale` flag is a JSON body field. A client that hits a cached response — through a CDN, a browser cache, or an intermediary — may receive a `stale: true` answer with cache headers that say it's fresh. The protocol says the client MUST treat it as stale, but the entire reason HTTP caching works is that clients don't parse bodies before deciding whether to use a cached response. A browser or HTTP library will serve the cached body based on headers alone. The only way to make `stale` win is to require `Cache-Control: no-cache` or similar during the grace window, which the protocol doesn't do. The rule as written is a client-side obligation that the wire format cannot express. A conformant HTTP cache will violate it by design.

**Fatal 2: The error matching rule (§7.1) is underspecified for non-reference implementations.** The text says: "The descriptor declares the error identifiers an origin can emit, exactly as it declares every other vocabulary — it declares the BARE identifier (`bad-job`), the wire `type` is an origin-relative URI reference whose FINAL PATH SEGMENT is that identifier, and a client matches on that final segment — no second mapping layer, no dereference, no descriptor-vs-`type` string comparison." The matching rule is clear for the reference case: `type: "/say/v0/e/bad-job"` matches descriptor token `bad-job`. But §6 says the `endpoints` field contains "URLs for ask, facts, changes, complaint as implemented" — and the descriptor table says the reference surface serves errors at `/say/v0/e/<id>`. A non-reference implementation could serve errors at any path, and the descriptor doesn't declare where error types are rooted. The `type` field is an RFC 9457 URI reference, which can be relative or absolute. If an origin serves errors at `/errors/bad-job` and the descriptor declares `bad-job`, the matching rule "final path segment equals identifier" still works — but nothing in the text says the final segment MUST equal the identifier for non-reference implementations. It says the reference surface does this. A second implementation could reasonably read the rule as "the type field is opaque, match the whole string against the declared set" and fail to match. This is fixable with one normative sentence, but as written it's a must-fix for interoperability.

**Fatal 3: The §5.2 fallback discovery rule creates a cache-poisoning / route-collision hazard with no origin verification.** The text says: "Discovery order for consumers: (1) HTTP `Link` / HTML `link` with `rel="service-desc"` on the human origin, then (2) if that fails, a single GET of the conventional descriptor path `/say/v0/index.json` on the same origin." The problem: step 2 is a guess. If a site doesn't implement Say, a GET to `/say/v0/index.json` will return whatever the site's 404 handler produces — which on many shared hosts is a 200 with a generic HTML page or a soft-404. The consumer's fallback parser must distinguish "this is a Say descriptor" from "this is a 404 page with a 200 status." The protocol provides no field that MUST be present to identify a valid descriptor (it lists minimum fields, but a soft-404 could theoretically be parsed as invalid JSON and discarded). More importantly, a malicious or misconfigured site could serve a descriptor at that path that was not intended as a Say surface. The protocol calls this a "fallback, not a new registry" — but it also says the surface is "the ORIGIN'S OWN STATEMENT" and that clients MUST treat it as such. The fallback path makes the origin's authority over its own descriptor ambiguous: if the human site doesn't link to `/say/v0/index.json`, is that descriptor authoritative? The text implies yes, but the site operator may not even know it exists. This is a route-collision hazard and an authority-ambiguity hazard in one.

## Ambiguities that will split implementations

**Ambiguity 1: The `grain` field's relationship to `where` matching is circular for non-token vocabularies.** §6 says the descriptor MUST declare a MATCH RULE for its geographic vocabulary, and defines `slug_exact_or_prefix` for slug vocabularies. But the text also says: "real businesses do not decide by a spec's list" and the descriptor may declare "radius classes" or other non-slug vocabularies. For those, the text says: "a declared rule MUST be specified well enough that an independent client can implement it without consulting the origin's operator." But it provides no normative guidance on what "specified well enough" means. A business that decides by "radius classes" could declare `match: "radius_from_postal_code"` — but what's the syntax? What's the radius? The spec says the client MUST NOT infer or approximate an ununderstood rule, and must treat those answers as `indeterminate`. That's clear. But it also says the origin MUST declare the rule. Two implementers reading this could: (a) define their own documented rule format and publish it, expecting clients to implement site-specific rules; or (b) restrict their vocabularies to `slug_exact_or_prefix` because it's the only rule the spec actually defines. Both are conformant readings, and they produce incompatible surfaces — implementer (a) builds a surface that most clients will read as `indeterminate` for all geographic answers, while implementer (b) builds a surface that actually works for clients. This is a split waiting to happen.

**Ambiguity 2: §7.1's `need` encoding is declared but not constrained.** The descriptor declares `need_encoding: "repeat_or_csv"` in the reference implementation, and §6 says "The reference descriptor declares both inside its `ask` block, as `need` and `need_encoding: "repeat_or_csv"`." But the normative text in §7.1 says: "`need` — an array of strings drawn from the descriptor's declared `need` vocabulary." An array in a GET request means repeated query parameters or a CSV string; in POST it means a JSON array. The text says the descriptor declares "how its members are encoded on the wire." But it doesn't specify what encodings are legal beyond the reference token `repeat_or_csv`. A second implementation could declare `need_encoding: "json_array"` for POST and `need_encoding: "pipe_delimited"` for GET, and both would be conformant. The spec's own example token (`repeat_or_csv`) is defined in §6 as "a GET `need` arrives as repeated keys or as one comma-separated value, and an origin advertising the token MUST accept both." But there is no closed vocabulary of encoding tokens. A client that understands `repeat_or_csv` but not `pipe_delimited` will treat the ask as an error or send the wrong format. This is exactly the divergence the `need_unknown` echo mechanism was designed to handle, but the echo only happens after the request succeeds — it can't help you formulate the request in the first place.

**Ambiguity 3: §9's change feed has no conformance test for "a fact class changed."** The text says entries "say that a fact class changed and `as_of`" and "changed" is "a fact class identifier from the site's own declared vocabulary, for example `hours` or `service_area`." But it doesn't say where the fact-class vocabulary is declared. Is it in the descriptor? Is it in the feed itself? If an origin changes its hours and its service area in the same day, does it emit two entries or one? If it changes hours twice in the same day, does it emit two entries with the same `as_of` date? The text says "The feed is a JSON array ordered newest first" — but "newest" by what? `as_of`? Sequence? Neither is specified. Two implementers could build feeds that are semantically equivalent but structurally incompatible, and a consumer polling the feed would have no way to know whether it missed an entry between polls. The text explicitly says "v0 does not require old-value diffs or a full history replay API" — which means missing an entry is permanent. Without a sequence number or entry ID (the text says stable per-entry identifiers are RECOMMENDED, not REQUIRED), a consumer polling every hour cannot detect that it missed two changes that happened within one polling interval.

**Ambiguity 4: §8's idempotency key "namespaced by key id" is undefined.** The text says: "In v0, idempotency keys are namespaced by key id." What is a "key id"? The descriptor's `auth` field mentions "where an origin also issues keys" — is "key id" the identifier of the rate-relief key from §11? If so, the idempotency key namespace is the client's API key identifier. But §11 says keys are "out of scope for the v0 wire" — so how does a client know its key id? And what if the client is anonymous? The text says "an operation that can create a durable obligation MUST NOT be offered anonymously without idempotency" — but if idempotency is namespaced by key id, and the client has no key (anonymous), what is the namespace? The origin's own identifier for the client? A random client-generated value? The text doesn't say. Two implementations could reasonably namespace by: (a) the client's IP address, (b) a client-supplied opaque token, (c) the literal string "anonymous" for all anonymous callers. These are all mutually incompatible and affect whether retries with the same `Idempotency-Key` header actually deduplicate.

## Adoption hazards

**Hazard 1: The publisher-only rot problem is acknowledged but the protocol's answer is a validator and a scoreboard that don't exist yet.** §1 says: "Publisher-only conventions without callers rot... This protocol is designed to ship with: 1. a consumer path (agents that actually ask), 2. a validator (conformance walks), 3. a scoreboard (measured cold decision cost)." But §19 gate 3 requires "Shadow data exists from at least one real deployment (callers + measured walks)" before the draft is final, and gate 4 requires "Model ratification round." The validator and scoreboard are described in §10 and §15 as future work or reference implementations. The adoption hazard is classic: the spec is written by people who understand the problem deeply (the drafting crews) and published to a world where nobody has a reason to implement it. The consumer path requires AI agents to actually send requests to `/say/v0/index.json` — but no major agent framework has a plugin for this, no browser extension implements it, and no orchestrator ships with Say support. The protocol's answer to the rot problem is "we'll build a validator and scoreboard" — but those are tools for the ecosystem, not the ecosystem itself. The spec needs at least one real consumer that isn't the authors' own test harness, and §19 gate 3 acknowledges this. But between draft and deployed, the rot window is open. The protocol should name a reference consumer implementation as a committed deliverable, not just a walk.

**Hazard 2: The descriptor's `valid_until` rule creates an operator maintenance burden that small businesses will not meet.** §6 says the descriptor expires, goes stale, and eventually returns 410 Gone on the descriptor. The rationale is sound: abandoned installs shouldn't serve dead facts. But in practice, a small business that installs a Say surface through a plugin or a shared host is not going to update its `valid_until` date manually. If the plugin auto-renews, that's fine — but the spec doesn't require auto-renewal. If the business forgets, the surface goes dark after the grace window. The spec's own change log says this was re-ruled to prevent fail-deadly behavior, but the underlying problem remains: the protocol requires ongoing operator action to keep a surface alive. This is the opposite of the "brake light" metaphor — a brake light doesn't need a calendar reminder to keep working. The `valid_until` mechanism is correct for abandoned installs but creates a new failure mode where a live business with a forgotten expiry date loses its machine door. The spec should require that implementations provide auto-renewal by default, or should make `valid_until` optional for L0/L1 deployments where the facts are static.

**Hazard 3: The no-directory poison pill (§13) will be read as hostile by the exact ecosystems that could drive adoption.** §13 says: "Bundling them into a multi-business discovery marketplace is a different product and MUST NOT be required to consume a single site's L1 answer." This is the correct scope decision — but the framing matters. The text says "Round-1 ratifiers argued agents prefer directories. That demand is real and out of scope on purpose." The risk is that the protocol gets positioned as "anti-directory" rather than "single-origin first." Directories and aggregators are how users actually find services. If the protocol's early public narrative is "we're not a phone book and we never will be," the directory ecosystems will ignore it, and without directories, the protocol has no consumer path at scale. The spec should include a positive statement about how directories can call Say surfaces as one input among many, and how an aggregator could implement Say on behalf of many origins without violating §13. As written, the poison pill reads as a statement of principle rather than a compatibility story.

## Harm scenarios

**Harm 1: `basis` fields are machine-readable redlining signals in disguise.** §7.1 requires every geographic `no` to carry a `basis` naming the operational reason: "distance, licensing territory, crew reach, seasonal." The intent is anti-redlining: force the origin to justify its refusal. But the effect is the opposite. A consumer or a third party can now harvest structured refusal reasons at scale — and "crew reach" or "seasonal" are exactly the euphemisms that redlining operations use. A discriminatory origin can answer `no` with `basis: "crew_reach"` for every majority-Black neighborhood and `basis: "distance"` for every white neighborhood at the same distance, and the wire format cannot distinguish legitimate operational constraints from discriminatory patterns. The spec acknowledges this in §10: "a tool MUST NOT label an origin discriminatory on pattern alone." But the machine-readable `basis` field makes the pattern trivially easy to produce, store, and analyze. The harm is not that the protocol enables redlining — redlining exists without it. The harm is that the protocol creates a clean, structured, machine-readable dataset of refusal reasons that is dramatically easier to use as evidence of (or a weapon for) discriminatory patterns than the human-visible website. The anti-redlining `basis` field is a double-edged sword, and the spec doesn't acknowledge this asymmetry.

**Harm 2: `agent.purpose: "audit"` creates a cover story for competitive intelligence and regulatory evasion.** §7.1 defines `agent.purpose` values including `audit` and says: "an origin MUST NOT vary the verdict or the substance of an answer by the declared purpose." The intent is non-discrimination between use cases. But a declared `audit` purpose is a public signal that the client is testing the surface. A malicious or overly cautious origin could respond to `audit` requests with carefully conformant answers (because they know they're being watched) and respond to `book_intent` requests with different, non-conformant answers (because those are real customers). The spec says the origin MUST NOT vary the verdict — but it provides no technical mechanism to prevent it. The `agent.purpose` field is advisory and self-declared. A client that wants to audit an origin can be detected and served sanitized answers. This doesn't just undermine the validator — it creates a false sense of safety. A regulated vertical (say, a lender using Say to qualify leads) could pass an audit with flying colors and then serve discriminatory answers to real applicants. The harm is that the audit mechanism gives the appearance of oversight without the teeth.

**Harm 3: Structured availability data for at-risk populations is a surveillance target, and the spec's own mitigation is insufficient.** §17 says: "Origins serving populations at risk (domestic-violence shelters, reproductive-health clinics, and similar) SHOULD weigh that structured availability answers make hostile polling cheap." The mitigation is: "such an origin may omit `open_now` and hours from machine answers, decline to light a Say surface at all, or answer with a declared refusal." These are opt-out mitigations. But the harm is not to the origin — it's to the people who need the service. If a domestic-violence shelter omits `open_now` from its Say surface, a person fleeing violence gets an `indeterminate` or a `no` and doesn't know whether the shelter is open. The parity principle (§2.3) says the machine surface should match the human site — but the human site probably also doesn't publish `open_now` for exactly this reason. The problem is that Say's existence changes the calculation. A shelter that previously had no structured availability data now has to make an active choice to not participate, and that choice itself is a signal. The spec says "decline to light a Say surface at all" is an option — but the absence of a Say surface is now, in a Say-adopting world, a signal that you might be serving an at-risk population. The protocol creates a new class of metadata (which origins have Say surfaces and which don't) that is itself a surveillance target. The spec doesn't address this at all.

**Harm 4: The record system (§8) creates durable evidence of service denials that can be used against consumers.** An L2 `yes` mints a record with a `rid`. But the protocol doesn't define what happens to the record after the transaction. §17 says: "Records MUST NOT store principal personal data unless the business transaction path defined outside this protocol actually requires it." But the record itself — the fact that on this date, at this time, an origin said `yes` to this job in this area — is metadata about the asker. In a divorce case, a custody dispute, an insurance claim, or an immigration proceeding, a record of a service inquiry could be subpoenaed or discovered. The spec says records are "unsigned" and "first-party assertion by the origin" — but that doesn't make them non-discoverable. The harm is that the protocol creates a new, structured, queryable trail of service inquiries that didn't exist before. The spec's privacy section focuses on personal data in the record, not on the existence of the record itself. A consumer who asks for quotes on a home renovation doesn't expect that the fact of their inquiry will be durable and retrievable. The spec should require that records be deleted after the transaction completes, or that `rid` values be unlinkable to the original ask.

## Patches

**Patch 1: Make the `stale` precedence rule wire-enforceable**

> Section: §6, Descriptor — `valid_until` and `stale`
> Current: "For a 30-day grace window after `valid_until`, an origin MAY keep answering: the descriptor MUST stay HTTP 200 and MUST carry `stale: true`, every answer body served in the window MUST carry the same flag, and a consumer MUST NOT present a stale artifact as fresh."
> Replace with: "For a 30-day grace window after `valid_until`, an origin MAY keep answering: the descriptor MUST stay HTTP 200 and MUST carry `stale: true`, every answer body served in the window MUST carry the same flag, and every response served in the window MUST include `Cache-Control: no-cache` (or a more restrictive directive) so that no conformant HTTP cache will serve the body without revalidation. A consumer MUST NOT present a stale artifact as fresh."
> Why: The current text relies on clients parsing a JSON body field before using a cached response, which is not how HTTP caches work. Adding a Cache-Control requirement makes the stale flag wire-enforceable.

**Patch 2: Close the error-matching ambiguity**

> Section: §7.1, Request — errors
> Current: "The descriptor declares the error identifiers an origin can emit, exactly as it declares every other vocabulary — it declares the BARE identifier (`bad-job`), the wire `type` is an origin-relative URI reference whose FINAL PATH SEGMENT is that identifier, and a client matches on that final segment — no second mapping layer, no dereference, no descriptor-vs-`type` string comparison."
> Replace with: "The descriptor declares the error identifiers an origin can emit, exactly as it declares every other vocabulary — it declares the BARE identifier (`bad-job`), and the wire `type` MUST be a URI reference whose final path segment (after the last `/`, percent-decoded) is exactly that identifier. A client matches the final path segment of `type` against the descriptor's declared identifiers; it MUST NOT match on the full `type` string, dereference `type`, or compare `type` to the bare identifier without extracting the segment. The origin may root its error `type` values at any path it controls."
> Why: The current text describes the reference implementation's behavior but doesn't state it as a normative rule for all implementations. This creates an interoperability split.

**Patch 3: Require a reference consumer implementation in §19**

> Section: §19, Publication gates
> Current: "3. **Shadow data** exists from at least one real deployment (callers + measured walks)"
> Replace with: "3. **Shadow data** exists from at least one real deployment (callers + measured walks) AND at least one independently maintained consumer implementation (not authored by the SayVel yard) has successfully queried a conformant surface and published its results"
> Why: The publisher-only rot problem is the single biggest adoption risk. Requiring an independent consumer before the standard is finalized ensures the protocol can actually be consumed, not just published.

**Patch 4: Require record deletion or unlinkability**

> Section: §17, Privacy considerations
> Current: "Records MUST NOT store principal personal data unless the business transaction path defined outside this protocol actually requires it."
> Replace with: "Records MUST NOT store principal personal data unless the business transaction path defined outside this protocol actually requires it. An origin that mints records MUST define and publish a retention policy for records, and SHOULD delete or unlink records (destroy the mapping between `rid` and the original ask) after the transaction the record supports has completed or been abandoned. An origin MUST NOT retain records indefinitely for analytics, marketing, or other secondary purposes."
> Why: The current text prevents personal data in records but not the durable trail of service inquiries, which is itself privacy-relevant and discoverable.

**Patch 5: Acknowledge and mitigate the `basis` field's double-edged nature**

> Section: §7.1, Request — Geography
> Current: "Every geographic `no` MUST carry a `basis` naming the operational reason (distance, licensing territory, crew reach, seasonal)."
> Replace with: "Every geographic `no` MUST carry a `basis` naming the operational reason (distance, licensing territory, crew reach, seasonal). Implementers and consumers MUST recognize that structured refusal reasons are themselves a dataset: `basis` values can be harvested, analyzed, and used to identify refusal patterns. An origin that serves a population or geography with a history of discriminatory service denial SHOULD weigh the risk that its `basis` values will be used as evidence in a pattern analysis, and may decline to answer geographically at all rather than serve structured refusals."
> Why: The current text treats `basis` as purely anti-redlining without acknowledging that it creates a new machine-readable dataset of refusal reasons. The patch preserves the anti-redlining function while adding an honest risk assessment.

**Patch 6: Define a minimum normative closed vocabulary of `need_encoding` tokens**

> Section: §6, Descriptor — `need`
> Current: "The reference descriptor declares both inside its `ask` block, as `need` and `need_encoding: "repeat_or_csv"`"
> Replace with: "The reference descriptor declares both inside its `ask` block, as `need` and `need_encoding: "repeat_or_csv"`. v0 defines exactly two conformant encoding tokens: `repeat_or_csv` (GET: repeated keys or comma-separated values, both accepted; POST: JSON array of strings) and `json_array` (POST only: JSON array of strings; GET: repeated keys). A client that does not understand a declared `need_encoding` MUST treat the ask as unanswerable and return an error to its caller. An origin MUST NOT use any other encoding token in v0."
> Why: The current text names one example token but doesn't close the vocabulary, creating an ambiguity where two implementations could use mutually incompatible encodings.

## Non-blocking nits

1. **§4 says "Ask" twice.** The Terminology section defines "Ask (the question)" and "Ask (operation)" as separate entries. This is intentional — the question and the operation are different things — but the typography doesn't make this clear. Consider "Ask (question)" and "Ask (operation)" with different formatting, or rename the operation to something like `ask` (lowercase, code font) throughout.

2. **§5.1 says the spec "does not mint a new well-known URI in v0" but §5.2 fallback is effectively a well-known URI.** The conventional path `/say/v0/index.json` is a de facto well-known URI. The spec's refusal to register `/.well-known/say` is a political choice, not a technical one. A future implementer will inevitably ask "why isn't this in `/.well-known/`?" and the answer ("we didn't want to mint a registry") will feel arbitrary. Consider adding a non-normative note explaining the tradeoff.

3. **§7.1 says an omitted `urgency` means `schedule`, but §7.6 says `urgency=emergency` means business urgency.** These are consistent, but the layering is confusing. A client that wants to express "this is urgent for business reasons" sends `urgency=emergency`, which reads as "this is a business emergency, not a life-safety emergency." The term `emergency` is doing double duty. Consider renaming the value to `business_emergency` or `urgent` to avoid the life-safety connotation.

4. **§15's performance targets are informative, but the token counts are specific to `o200k_base`.** The spec says "Publish measurements with method, not vibes" — good — but then cites a specific tokenizer without defining what it is or why it's the reference. A reader who doesn't know what `o200k_base` is (most people) will see an unexplained number. Add a one-line definition or a footnote.

5. **§20a's change log is unusually long for a non-normative section and risks being read as normative history.** The change log is positioned as a public record of the drafting process, which is valuable. But at ~3,000 words, it's longer than some sections of the normative spec. A reader skimming for requirements might accidentally absorb a change-log decision as a current rule. Consider a one-line note at the top of §20a: "This section records past decisions. The normative text above supersedes any statement here that conflicts with it."

6. **§22's signature table lists "Ratifying models" with status "Round opens after Beacon countersign" — but Beacon's signature is already recorded.** The table is stale. If the round is open, the status should reflect that. If the round is not open, the draft should say so at the top. As written, the signature table implies a state (pre-round) that contradicts the document's status (DRAFT, gates pending).
